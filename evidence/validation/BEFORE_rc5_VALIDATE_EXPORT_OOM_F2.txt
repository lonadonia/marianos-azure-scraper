F2's export validation on Hamza's VM: killed by the kernel for lack of memory (a defect found in this review)

What ran. `validate-export --run 01M7JNB2HDFCNR3GHQVX8FYXX6` (1.10.0rc5, offline: no provider request), twice:
  1. by the stage harness right after F2's last slice (stage_evidence.sh, about 19:01Z): exit 1, no output line
     (runs/F2d/COLLECT.log, runs/F2d/validate_export.jsonl, empty);
  2. again through the collector's wrapper at about 19:22Z, to confirm: exit 1, no output line.
Both times the kernel's out-of-memory killer ended the process (the lines below, read with `dmesg -T` on the VM,
clock UTC; the first process is named python because the harness runs the collector's module, the second
marianos-collec, the collector's command).

Why. For a run, validate-export reads the decompressed text of every stored listing page of the run into memory
before it indexes them (operations.py, validate_export: the `html` list, then source_check.index). F2 has 575
stored listing pages; the process held about 3.3 GiB when it was killed (anon-rss, in KiB, below), on a VM of
3.8 GiB (MemTotal) without swap. Memory
grows with the number of pages, so a full run (about 3,000 to 4,800 listing pages) could not be validated there
either. The record-level checks that need no stored page passed: the 22-field contract of both export files
(F2_CONTRACT_CHECK_products.json.jsonl and F2_CONTRACT_CHECK_products_fresh.json.jsonl, `validate-export
--file`, exit 0: 8,104 and 7,678 rows, no duplicate UPC or URL). The collector's own check of every record against
the stored pages did not complete for F2; the independent check of sampled records against their tiles is in
../samples/ (check_sample.py).

Correction (open, Hamza, offline, no credit): read and index the stored pages one at a time, so memory stays
bounded by one page; a regression that bounds it; then run validate-export on F2 again.
